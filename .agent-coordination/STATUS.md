## 2026-07-30 — First full-scale validation found critical, real bugs; architectural fix landed

Ran the full 6-shard validation against the real `packages/ui` suite. Results were bad, and correctly so — this is exactly what this validation step is for. Full findings (verbatim from the validating agent, not summarized away):

1. **Count reconciliation failed hugely** (raw sum ~22,672 vs the ~7567 baseline). Root cause pinned down precisely: `TesterMixin.createTestCommand`'s "always include optimized test files even when paths would otherwise be skipped" check only matched the literal substring `.test_optimizer.dart`, which generated *combined* bucket files contain but a *solo* (quarantined) file's own raw filename does not. So under the real CI invocation shape (`sip test --experimental-bucket ...` with no explicit path — exactly cushions' actual usage), a solo file's command args got silently wiped to `[]`, causing `flutter test` to fall back to discovering and running the **entire package** instead of just that one file. In 2 of 6 shards this silently re-ran nearly the whole 582-file suite; in 1 shard it instead crashed on a native-asset tooling race, meaning that shard's designated quarantined file **never ran at all while the overall command still exited 0.**
2. **A second, deeper architecture bug** explained the timing failure and the high per-shard bucket-failure rate: I had been dispatching **one separate `flutter test` OS process per bucket/solo file** within a shard (using sip's own concurrent script-runner), rather than the prototype's actual design of **one `flutter test` invocation per shard, given all its bucket/solo files as multiple positional arguments**. This meant: (a) Flutter's fixed per-invocation bootstrap/native-asset-build cost was paid once *per bucket* instead of once *per shard*, and (b) those multiple concurrent `flutter test` processes raced on the same package's `build/native_assets` directory — reproducing, *internally, within a single shard invocation*, the exact cross-process race condition this task's brief explicitly warned about for concurrent shards. This is almost certainly why 8 of 12 buckets across the run showed 100%-missing-coverage fallback triggers, why one shard crashed outright, and why max shard time (2520s) was worse than the entire unsharded baseline.
3. A genuine, different-mechanism cross-file contamination case was also found (`event_card_test.dart` failing only when combined, passing standalone 34/34) — a leak vector (looks like image-cache/async-timing related) that the current two safety checks don't cover. Noted for the record; not something a static check can catch, consistent with the brief's own acknowledgment that hazard 3 is fundamentally unpatchable by pattern-matching. The runtime fallback net is the mitigation for this class of bug, and it depends on items 1/2 above actually working correctly, which is why I fixed those before treating this as acceptable residual risk.

**Fix implemented** (this was a real architectural correction, not a patch):

- `Package.testGroups` now always returns exactly **one** group per bucket-mode invocation — every bucket file *and* solo file assigned to this invocation (the whole plan, or just this shard's slice), as multiple arguments to one `flutter test` command. Never one command per bucket again.
- Solo (quarantined) files are now **also** generated as their own trivial single-file wrapper (a "bucket of one", reusing the exact same `group('<original file>', ...)` mechanism), instead of being dispatched via their raw path. This turned out to be necessary for a subtler reason found while re-verifying empirically against real `dart test` output: **`dart test`'s CI reporter only prefixes results with the physical suite file's path once more than one file is passed on the command line** — a raw solo file sharing an invocation with anything else would otherwise be unidentifiable in the output (always looking "missing", or never matching its own coverage check). Wrapping it the same way as a real bucket makes it identifiable via its own injected group name regardless of invocation shape. Confirmed this doesn't reintroduce hazard 1/2 (nothing else shares that file's isolate).
- The fallback-on-failure mechanism now discards and re-runs at the correct granularity: **per bucket/solo group**, not per whole shard-command. If one bucket in a 2-bucket shard invocation is compromised, only that bucket's original files are discarded and re-run; the other, healthy bucket's results are left untouched (previously — before this fix even existed as multi-bucket-aware — this distinction didn't apply since each bucket got its own command; this is the necessary counterpart to combining multiple buckets into one shard invocation).
- Also had to fix the coverage-detection logic itself: confirmed empirically (via real `dart test --reporter`-equivalent runs, not just reading source) that the injected group name lands in `TestOutput.path` for a single-file invocation but gets pushed into `TestOutput.test` (with the physical wrapper file taking `path` instead) for a multi-file invocation — now checks both fields.
- `createTestCommand`'s path-stripping bug (item 1 above) is structurally fixed by an explicit `isBucketCommand` flag now, not by string-matching a generated filename that may or may not be present — robust regardless of whether a shard's invocation happens to contain zero real combined buckets (all-solo shards were the sharpest edge case for the old logic).

Added/updated unit tests for all of the above (one-group-per-shard `testGroups`, solo-file wrapper generation, the new `bucketFileGroupsFor` helper, and a new test specifically covering partial-group fallback: one compromised bucket's files get discarded+re-run while a healthy bucket sharing the same invocation is left alone). Full suite (224 tests) green, `dart analyze --fatal-infos --fatal-warnings` clean, `dart format` clean, reinstalled locally. Starting a second full-scale validation run now to confirm this actually holds up against the real suite before calling this done — the first run earning a "not safe to ship" verdict is exactly why this second pass matters more than the first.

## 2026-07-30 — Second full-scale validation: fix confirmed, feature ready. Final summary.

Second validation run (fresh 6-shard sequential run against the real `packages/ui` suite, same shape as before, `--coverage --coverage-package=couchsurfing_ui`) confirms the architectural fix actually works:

- **Structural confirmation**: every shard genuinely dispatched as ONE `flutter test` invocation carrying multiple bucket/solo file arguments together (verified directly from log `Test command:` lines, e.g. `flutter test ... test/.test_optimizer_bucket_0.dart test/.test_optimizer_bucket_6.dart test/.test_optimizer_solo_0.dart`) — no more one-process-per-bucket.
- **No crashes.** No native-asset-race symptoms in any of the 6 shards (previously: 1 outright crash, most buckets showing 100%-missing fallback triggers).
- **Count reconciliation: ~7573–7577 vs. the ~7567 baseline** (within ~0.1%) — a dramatic fix versus the first run's ~22,672 (3x inflation from the solo-file bug).
- **Solo dispatch verified correct**: all 3 known quarantined files (`post_screen_comment_performance_test.dart`, `post_screen_comment_reply_reaction_test.dart`, `post_screen_reply_comment_test.dart`) ran only their own tests, in their own generated single-file wrapper — no whole-package re-discovery.
- **Fallback mechanism exercised for real, by real bugs, and worked correctly.** Two shards hit genuine pre-existing problems in `cushions` itself — a compile error in `channel_screen_attachment_bottom_sheet_test.dart` (stale `cross_file`/`XFile` type mismatch) and a misnamed non-test file (`setup_app_review_for_test.dart`, matches the `_test.dart` glob but has no `main()`) — each of which crashed the shared compiler session for its whole shard. In both cases sip correctly discarded the compromised results and re-ran every original file in that shard as one combined non-bucketed fallback invocation; the ~97 unaffected files in each shard produced correct results, and only the one genuinely-broken file failed again (as it always would, bucketed or not). This is exactly the fallback mechanism working as designed, under real conditions, not a synthetic test.
- **Timing: clean shards ran 72–121s, right in line with the ~111s prior-prototype figure. Max shard time 179.73s vs. the ~13–16 min unsharded baseline — a ~4.4–5.3x real, credible speedup**, and nowhere near the first run's 2520s-max regression.
- **`event_card_test.dart` cross-file contamination is still present** (fails only when combined, passes standalone 34/34) — confirmed this is a genuinely different leak mechanism than the two hazards `FlutterTestSafety` checks for, and is NOT something this fix was expected to address. This is the same class of "unfixable by static pattern, and not always caught by the runtime fallback either" risk the original brief explicitly flagged for hazard 3 (the file DOES report a result, just a wrong one — coverage-based fallback detection has no way to know that). Documented this explicitly in both the CHANGELOG entry and the `--help` usage text so it isn't oversold as a complete safety guarantee.
- **One new, pre-existing, out-of-scope finding worth flagging separately**: `sip test`'s results tally and exit code don't account for a file that fails to *load/compile* at all (confirmed this reproduces with a plain non-bucket `sip test <broken-file>` too — nothing to do with bucketing). A shard that falls back due to a genuinely-broken file will still exit 0. Did not fix this — it's a general reliability gap in sip's existing CI-output-parsing approach, unrelated to and outside the scope of this task, but real and worth a follow-up ticket. Flagging here rather than silently leaving it undocumented.
